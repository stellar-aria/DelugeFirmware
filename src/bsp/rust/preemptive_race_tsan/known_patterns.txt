# Lens 2 (Task 9) TSan classifier: KNOWN, pre-existing, BROAD debt patterns.
#
# One extended-regex PATTERN per line (matched with `grep -E` against a normalized TSan
# `SUMMARY:` line — see run.sh's `normalize()`). Blank lines and `#` comments are ignored.
# Order matters: run.sh checks `open_findings_patterns.txt` FIRST, so a line matching both
# (e.g. `loader.cpp:82` below, which is inside a file this list's broad `loader\.cpp`-style
# reasoning would otherwise also catch) is correctly bucketed as an open finding, not here.
#
# WHY PATTERNS, NOT EXACT LINES: an early version of this catalog used exact `SUMMARY:` line
# matches (Spike B's style). Running the harness fresh a few more times immediately produced
# a LONG tail of new exact lines — different song-load/UI/Arpeggiator/reverb fields lit up
# by run-to-run scheduling variance — all belonging to the SAME already-understood debt
# class: nearly the WHOLE app's main-thread/UI/song-model/reverb/playback-transport state was
# written assuming cooperative (non-preemptive) scheduling, and none of it was made
# thread-safe when the audio task moved onto its own real preemptive OS-thread/interrupt
# executor (a change that predates this task — see the embassy-scheduler-migration and
# audio-callback-relocation work). Exact-line matching against that class is an unwinnable,
# ever-growing whack-a-mole; a broad FILE/SUBSYSTEM pattern is the honest, maintainable
# classification — it says "yes, this is that same well-understood, out-of-scope debt",
# without pretending to have enumerated every specific field it can touch.
#
# What stays OUT of this file (by design, so it is never accidentally swallowed into "known,
# ignore"): anything on the actual storage/cluster/recorder/resource-manager data path this
# task exists to check — see open_findings_patterns.txt for that (checked first).
