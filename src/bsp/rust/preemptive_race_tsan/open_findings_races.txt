# --- deluge_resource::manager::Manager's Cell<ChunkSlot> chunk table: Manager::release
#     (audio thread, via Voice/SampleLowLevelReader unassign -> cluster::remove_reason ->
#     release_lease) races Manager::loader_next (loader/fiber thread, picking the next
#     queued cluster to load) on the SAME Cell<ChunkSlot> slot, and other combinations
#     (loader_enqueue/loader_remove/acquire/request/evict_lowest could plausibly hit the
#     same table too, given they all just Cell::get/Cell::set with no synchronization) —
#     Manager was written as `single-threaded` (see its own `stat()` doc comment) but is
#     reached from Rust-unsafe `extern "C"` entry points with no lock, so nothing enforces
#     that assumption once C++ calls it from two real OS threads. HIGH severity: a
#     non-atomic read-modify-write race on lease counts / queued flags can silently lose an
#     update (a lease undercounted -> premature eviction of a still-playing cluster, or a
#     queued flag never cleared -> the loader spins on a phantom queue entry).
Cell<deluge_resource::manager::ChunkSlot>
core::mem::replace::<deluge_resource::manager::ChunkSlot>

# --- SampleRecorder/SampleStream recording-cluster state: SampleRecorder::createNextCluster()
#     (audio thread, real-time capture path — increments currentRecordClusterIndex and grows
#     SampleStream's table_ std::vector<SampleCluster>) races SampleRecorder::cardRoutine()
#     -> writeOneCompletedCluster() -> SampleStream::chunk_at() (loader/fiber thread, the
#     card-write drain) on the SAME currentRecordClusterIndex field and the SAME table_
#     vector. HIGH severity, worse than the ChunkSlot race: `table_` is a growing
#     std::vector — if it reallocates (moves its backing storage) on the audio thread at the
#     exact moment the fiber thread is mid-index into the OLD backing array, that is a
#     genuine use-after-free / OOB read, not just a torn value (a real, if narrow-window,
#     crash/corruption hazard during sustained recording, not merely a benign lost update).
in SampleRecorder::cardRoutine\(\)
in SampleRecorder::createNextCluster\(\)
in SampleRecorder::writeCluster\(int, unsigned long\)
in deluge::audio::stream::SampleStream::chunk_at\(unsigned int\) const
in deluge::audio::stream::SampleStream::entry\(unsigned int\)

# --- The same recording path's raw payload buffer: audio-thread std::copy_n (feeding
#     captured samples into the in-progress record cluster's buffer, via
#     std::__copy_n_a/__tsan_memmove) races the fiber thread's real `write(2)` syscall
#     (deluge_bsp::sd::host::write_sectors) writing that SAME buffer's bytes out to disk —
#     the fiber can read a torn/half-written buffer if the audio thread's copy lands
#     mid-write. Same root cause as the two entries above (SampleRecorder's cluster
#     hand-off from audio-thread producer to fiber-thread consumer has no synchronization),
#     not a separate bug. The generic compiler-helper symbol names below (`in write`,
#     `in __tsan_memmove`) are ambiguous on their own — confirmed by manual trace inspection
#     (see the report) that all observed instances traced to this SampleRecorder hand-off,
#     both racing on the `deluge_rust::services::HOST_SDRAM` region; re-verify the paired
#     stack before treating a future match as this same finding rather than something new.
in write$
in __tsan_memmove$
in __tsan_memset$
in __tsan_memcpy$
